Warden — Behavioral Key Defense & Bank-Change Gate

Stack: Next.js 16, TypeScript, Tailwind, shadcn/ui, Supabase (PostgreSQL, row-level security)
Security Engines: Frozen baseline, CIDR address limits, hashed-key vault, secret scanner
Validation: 24/24 browser tests, 119 live-database checks, 74 unit tests, E01–E19 evidence

1. Objective & Architecture

Warden is a defensive control layer for the gap in this case: a valid third-party key was misused to reach finance data and change a supplier’s bank account. It learns each key’s normal behavior, enforces per-key limits at a gateway, holds unapproved bank changes for a call-back and two people, and tests the vendor’s claims against the logs, through four decoupled modules:

ModuleEngine RoleCore Defensive Controls
src/engineBehavior & Evidence EngineReads logs by their columns, so any filename works. Learns each key’s usual hosts and actions, frozen at mid-span. Groups alerts (240 flagged events become 23 groups). Checks approval references (E19), ranks key risk, tests 8 vendor claims, scores itself, replays the attack.
Key vaultKey Control GatewayHashed secrets, timed auto-rotation with a grace window, per-key address ranges (off / monitor / enforce), scope limits, automatic cut-off (quarantine or revoke). Source address trusted only from the gateway. Live risk score with reasons.
Bank gateMoney ControlHolds bank changes with no or out-of-sequence approval, made through the API, or after a recent contact change. A key can never apply a change. Release needs an analyst’s request and a different approver.
Access & ticketsIdentity & Secret GuardSign-in required; viewer, analyst, approver, admin and vendor roles enforced by the database; audit log. Ticket scanner refuses secrets, alerts an admin and rotates a leaked live key.

2. Multi-Layer Defense Mechanisms

  • Frozen Behavioral Baseline: Learns each key’s usual hosts and actions from the first half of the logs, then freezes it, so the attacker’s own traffic cannot become “normal”. Measured: 237 of 237 attack events detected, 0 false alarms in 41,616 ordinary events. Unchanged with renumbered hosts and shifted clocks; 177 of 237 if the attacker rides a real sync computer.
  • Bank-Change Gate: The case’s V-0412 change (****4417 to ****9083, E19 line 313) and V-0233 (E19 line 243) are held before payment. Release takes a call-back, an analyst’s request and a different person’s approval.
  • Key Containment & Trusted Source: A claimed private address is ignored; a private address arriving from the public internet is blocked as forged. Every call is judged ALLOWED, SUSPICIOUS or BLOCKED, with a 0–100 risk and reasons.
  • Secret Scanner: Tickets and comments are scanned for keys, tokens, private keys and passwords before saving (the TKT-48213 pattern). A hit is refused, an admin is alerted and a live vault key is replaced at once.

Security Boundary & Deployment: Warden sits beside the systems it protects, so a compromise of one cannot switch the defense off. Today it analyses the real exported case logs (109,061 events in about 1 second) and enforces on a simulated LedgerOne / HelpDeskr / BlueVault gateway holding made-up data. Live use needs each system’s log feed and a gateway check. It pairs with, and does not replace, endpoint antivirus. Launch locally via npm run dev.

Limitation: Our suspicious-activity labels are our interpretation of the logs, so results show how consistently the rules agree with it, not attacker identity or performance in every real environment.
