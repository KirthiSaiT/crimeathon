Problem Statement – Case CR-26-047 (Tier 1)

Team: H4CK_077  |  Approach: DEFENSE  |  19 Nov 2026

1. What we believe happened

Leaked machine keys were used to read H&F's support, file and finance data and then to change a supplier's bank account. A BlueVault key (bvk-7f3a) was pasted into ticket TKT-48213 on 25 Jun and never removed or rotated. An unknown actor then used TallyBridge's HelpDeskr admin key (tb-sync-svc) to search tickets for secrets and opened only that ticket. Three days later the BlueVault key was used from new addresses to read finance files. With TallyBridge's finance key (key-tb-07) the actor copied supplier data in August. From 17 Aug a host on TallyBridge's private link (10.20.4.77) searched payments and bank details. On 3 Sep it changed vendor V-0412's bank account with no approval reference, five days before the 8 Sep payment run. TallyBridge's notices understated all of this.

2. Key findings (evidence IDs)

  • Keys were over-powerful and unreviewed: E04 shows key-tb-07 (read/write all modules), tb-sync-svc (admin) and bvk-7f3a (all folders), all with no IP limit, no expiry; reviewed Jun 2024 / Feb 2025. E10 s2.1-2.3 require IP limits, 90-day expiry and minimum scope.
  • Secrets in tickets were known and unfixed: E13, E10 s5.1-5.2, E11 finding 2 (High, Open), E09 R-025 and R-029 overdue.
  • The stolen key had no normal finance use: E05 shows 995 normal reads from 172.16.9.40 and none in /finance; no staff account reads the two bank-instruction files.
  • The bank-details endpoint has no normal use: only key-tb-07 ever calls it (E01, E18); the six sync nodes (.11-.16) never do.
  • Cost signal ignored: E06 shows 13 export jobs by 24 Aug and 14 in August vs 4 in July, matching 10 attacker exports plus the weekly Tuesday export (E02).
  • Same-day probe: three failed logins on the IT admin from 198.18.7.77 on 15 Aug (E03 l.22438-22440) while that address read finance files (E05).
  • Vendor account contradicted: E16 ("no finance or files, nothing on the private link, rotated, closed") vs E01, E05, E15, E04; E12 went to the billing mailbox only; E17 omits .23/.24/.77 and 10.20.4.77, lists a python user agent absent from E01, and starts on 11 Aug although E01 shows activity on 9 Aug.
  • Approval control gap: E19 has 4 bank changes with no approval_ref (3 UI by Finance staff, 1 API: V-0412). R-015 covers payment runs, not vendor-record changes (E09).

3. Uncertainty and what would resolve it

  • How the actor got key-tb-07 and tb-sync-svc: we infer TallyBridge's side (E15, E07 audit gaps, E20-E forum posts) but it is not shown. TallyBridge's vault and build-host logs.
  • Whether the outside actor (198.18.7.x, client 3.4.1, ~03:00 UTC) and the build-host actor (10.20.4.77, client 3.5.0, ~12:10 UTC) are one party: the link is shared keys and goal, not a log. Logs of host tb-build-02; who owns 10.20.4.77.
  • Whether V-0412 is in the 8 Sep run and whose account ****9083 is. Payment-run list and a call-back to the vendor.
  • BlueVault clock offset; two finance reads with a blank address (E05 l.6492, 6527); E15 host labels are vendor-supplied.

4. Alternative explanations considered

  • Legitimate 3.6.0 contact sync (E20-C): ruled out; it changes contact fields from .11-.16, not bank details from .77.
  • Finance clean-up or audit (E19, E13): ruled out; bulk changes use IMPORT with a BULK ref and the UI, never the API; the 22 Jul export-and-delete and 31 Jul import were announced.
  • 9 Jul sandbox traffic from .77: set aside; matches announced maintenance (E15, E20-B).
  • Staff on the same address range: set aside; 198.18.0.0/16 is a shared dynamic pool (E20-G), so an address does not identify a person.
  • Former employee R. Menon's kiosk login (E03, E14): a real offboarding gap, no link to this chain. Finance's V-0233 change with out-of-order APR-1182 (E19 l.243): unresolved, kept separate.

5. The problem we chose, and why

A leaked machine key can read finance data and change supplier bank details, and no control connects the signals across systems or stops the change before the payment run.

What failed: keys had no limits (E04); secrets sat in tickets (E13); nobody watched exports or off-profile use (E10 s4.1, E11 finding 6); bank changes needed no enforced approval (E19); the vendor was trusted on its own word (E07, E08). Why this problem: it is where money is lost, it is time-critical (a payment run 5 days after the change), and it can be tested on the supplied logs.

6. The obvious approach, and why we are not taking it

Obvious: rotate keys, add IP allowlists, write per-system anomaly rules. Not taken because the decisive call used the right key and a private-link address inside the sync window (E18): an allowlist that includes 10.20.4.0/24 passes it, and per-system rules see one normal-looking call. A keyword scanner would also false-alarm on staff searches such as "password reset" and "api key request" (E02).

Our idea: (1) normalise the clocks (UTC, IST, epoch) and names (key-tb-07 = tb-sync-svc = host labels); (2) learn each key's normal hosts, endpoints and hours from a baseline frozen before the incident; (3) flag off-profile use, secret-search and export-delete cycles by integration accounts, and any call to the bank-details endpoint; (4) require a valid approval reference on every bank change and hold the supplier for call-back before the payment run; (5) check each vendor claim against our own logs.

7. What could change our conclusion

Vendor proof that 10.20.4.77 is a sanctioned node; an approval record for V-0412; a call-back showing ****9083 is the real vendor's account; logs showing the keys leaked from H&F; or an unseen record linking the build host to normal vendor maintenance.

8. Selected approach and test plan

DEFENSE (locked). We will report correct detections, false alarms and misses on the supplied data and on varied copies (renumbered hosts, shifted clocks, an attacker using a real sync node), and show that ordinary events are not flagged: nightly sync, 3.6.0 contact updates, Tuesday exports, Finance's bulk import, remote staff on shared addresses. Preliminary: a prototype caught all 203 labelled attacker events with 0 false alarms; with an attacker on a real sync node it still caught every API and HelpDesk event but missed 70 raw network flows. Limits: the labels are our own attribution, so results show consistency, not proof of generality; a baseline learned from tainted data degrades detection, so it must be frozen.
